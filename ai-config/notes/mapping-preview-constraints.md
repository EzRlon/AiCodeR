# 映射预览功能的用户硬约束（2026-10-11 明确）

用户要做「被测应用界面映射到 AiCode 本体 + 标注质检账本」功能时的硬性要求：

- **不借助 adb**（Shizuku 也被归为「额外搭桥」，不采用）
- **不需要软件本体之外的任何额外/增强权限**（不申请投屏、无障碍等系统级敏感权限）
- **必须复用已有容器**实现（同 VNC/浏览器链路：容器跑服务 → 本体 WebView/面板消费）
- 软件内闭环、足够高效即可，形式不限

## 技术事实（已向用户说明）
- PRoot Linux 容器无法运行原生安卓 APK（需要 Android 运行时），这是平台物理约束，任何 App 都绕不开——Google Stitch 也因此做成 Web 设计稿而非运行真 APK
- **正确路线 = 复刻浏览器方法**：被测界面以容器可渲染的 Web 形态开发/编译（HTML/JS），容器内起 HTTP 服务，AiCode 本体 WebView 加载 + 标注层 + Room 账本，全链路软件内、零新增权限
- 对原生 APK：如实告知需系统安装（普通安装权限，非额外增强权限）或投屏（用户已排除），引导采用 Web 预览路线做 UI 迭代层

## 一期共识方向（待用户确认后进 PLAN）
截图标注账本（纯 App 内）→ 容器 Web 预览映射（浏览器方法复刻）→ 账本状态机（待确认→已发AI→修复中→待复验→关闭）

## 体积精简原则（用户 2026-10-11 追加强调）
- 参照的「虚拟大师/光速虚拟机」类产品 2G+ 体积属于完整系统 VM 路线，本项目不采用
- 定稿架构（UI 在映射处本地渲染 + 算法在容器）真实增量：Web 预览层≈0（容器已有 Python/Node，零新增运行时）、账本<1MB、可选沙箱引擎仅 5-10MB（应用级虚拟化无系统镜像、无双份运行时，只有假框架+被测 App）
- 沙箱为可选模块默认不启用，按需开启；不做完整系统镜像
- 实时反馈机制定稿：容器文件监视+WebSocket 推送刷新（AI 改完预览自动更新，用户无需手动刷新）；界面与算法双通道独立热更
