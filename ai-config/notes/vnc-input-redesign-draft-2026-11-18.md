# VNC 触屏鼠标操作重设计（草案 v1，待两轮辩证）

2026-11-18。用户判定当前实现（b20，触摸→合成 MouseEvent 方案）效果很差，要求：先重新设计、经过两轮辩证、再动手。

## 一、用户既有的资料与想法（约束输入）

1. **参考资料**：Winlator（TouchpadView：相对/绝对双模式、双指右键、双指滚动、加速 1.25×）、Limbo（usb-tablet 绝对定位、轨迹板双击切换、VNC 鼠标校准修复史）。
2. **既有反馈脉络**：
   - 早期：noVNC 默认手势在手机小窗「点不准」→ 用户接受触控板思路；
   - 11-16：光标巨大（noVNC 触摸回退画布按远端像素画）、移动不准（要么挪不动要么飞过去）→ 当时用自绘光标+非线性加速压住了现象；
   - 11-18（今天 3 张截图标注 + 「效果很差」）：b20 的触摸→MouseEvent 方案仍然不行。合成事件这条路（自换算+全屏捕获层 patch）证明脆弱。

## 二、候选方案

### 方案 A：noVNC 官方触摸手势，不写输入层（删代码路线）
让 noVNC 的 GestureHandler 直接处理触摸：单指点按=左键、双指=右键、三指=中键、长按=拖动、双指滑动=滚动。
- 优点：零自研、随 noVNC 升级；行为与官方 demo 一致。
- 缺点：无「触控板」相对模式（手机小窗点不准的问题会回来）；光标巨大问题依赖 noVNC 自身修复。

### 方案 B：虚拟指针 + 相对事件（触控板为主模式）
App 侧维护一个虚拟指针（屏幕坐标），单指滑动驱动它移动（加速），点击/长按/双指都作用在虚拟指针位置；发送仍走 noVNC 公开事件。
- 优点：小窗精确定位；指针大小由远端绘制。
- 缺点：仍有自换算逻辑；与 noVNC 手势层的冲突要靠事件捕获层级管理。

### 方案 C（推荐基线）：**原生层双模式 + 明确语义，触摸事件在原生 Compose 层处理，不再走 WebView 合成事件**
把输入处理从 WebView 里的 JS 挪到 Android 原生（VncOverlayWindow 已有的 Compose pointerInput），原因：
- Android WebView 的触摸→合成 MouseEvent 存在捕获层、坐标缩放、事件时序三类已知坑（b20 全踩了）；
- 原生层拿到的是原始 MotionEvent，可以做 Winlator 同款双模式：
  - **直触**：手指位置=指针位置，1:1；按下即 mousedown，移动即拖动；
  - **触控板**：虚拟指针+加速（阈值 10px、1.25×），点击/长按/双指手势作用于虚拟指针；
- 事件通过 JS 桥调用 noVNC 公开 API 发送鼠标（rfb.sendPointer? 若无公开 API，则用 XServerDisplayActivity 思路自管协议——见辩证点 3）。

## 三、辩证点（供两轮辩论）

1. **输入处理层放哪**：WebView JS（b20 路线，已证明差）vs 原生 Compose 层（方案 C）vs 两者混合？
2. **默认模式**：直触优先还是触控板优先？切换入口放哪（标题栏按钮 vs 控制条）？
3. **发送协议**：noVNC 只有私有 _sendMouse。三条路：a) 继续用私有 API（升级会碎）；b) fork noVNC 加公开 sendPointer(x,y,button)；c) 绕过 noVNC，原生层直接实现 RFB pointerEvent（协议只有 6 字节）。
4. **光标显示**：远端自绘（真实形状，但小窗里可能太小）vs 本地虚拟光标叠加（可控大小，但可能与远端位置偏差）。
5. **滚动方向与速度**：自然滚动（手指上滑内容上滑）vs 传统（滚轮向下）；是否需要滚动灵敏度设置。

## 四、验收标准（两轮辩证后冻结）

- [ ] 单指轻点：点中目标，误差 ≤ 半个控件高度
- [ ] 单指拖动：可拖窗口/滑杆，中途不断
- [ ] 双指轻点 = 右键；双指滑动 = 滚轮（方向符合所选习惯）
- [ ] 触控板模式：慢速微调可达 1px 级；快速滑动一次可横跨屏幕
- [ ] 连续操作 20 次无卡死/无响应丢失
- [ ] 光标大小与位置始终与实际操作点一致
- [ ] noVNC 升级不破坏输入层（不依赖私有 API）

# v2 设计（吸收第一轮辩证，2026-11-18）

## 第一轮硬结论（两方一致）
- 原生绕过 noVNC 自发 pointerEvent：判死（ws 句柄在 JS 闭包；双连接=双带宽+乱序）。
- 事件投递必须在 JS 层；原生最多做手势决策经桥转发。
- b20 三大算法 bug：加速按单事件位移（应累计/按速度）；滚动未放大（50px/格太钝）；合成事件绕过手势路径致 noVNC 本地光标不更新（点不准主因候选）。

## v2 架构
**模式一「直触」（默认）= 不写输入层**：删除现有全部触摸接管，让 noVNC GestureHandler 官方手势直接工作（onetap=左键、twotap=右键、threetap=中键、longpress=右键、drag=拖动、twodrag/pinch=滚动缩放）。零自研，行为=官方 demo，升级不碎。
- 保留：点画面唤起键盘、右下控制条（右键/中键显式入口）。

**模式二「触控板」（显式开启）= 合成事件 + 自绘光标，修三处算法**：
1. 加速按「手势内累计位移」：一次滑动手势累计 dist，speed = 1 + min(2, dist/120)（慢滑≈1:1，滑满 240px 达 3×），事件间连续累加到虚拟指针；手势结束清零。
2. 滚动放大：双指 dy×4 再喂 noVNC（它仍按 50px/格累积），一格约 12px 滚动量，接近桌面手感。
3. 点击纪律：mousedown/mouseup 严格成对；每次 mousedown 前先发同坐标 mousemove（把 noVNC 的 _mousePos 拉到位）；手势开始时先发一次中心 mousemove。
4. 自绘小光标回归（b18 已验证可接受的 12px 圆环）：触控板模式下显示在虚拟指针处；直触模式隐藏（远端光标即指针）。这解决「合成事件下 noVNC 本地光标停旧位」——我们自己画，不依赖 noVNC 的 _cursor。
5. 长按（500ms 内未动）= 右键（b18 语义，Android 直觉），拖动阈值 8px。

**纵横比**：去掉 CSS !important 强改 canvas 尺寸，改由 fitScreen 后读取 canvas 真实内部分辨率，若与容器纵横比差 >2% 则调 xrandr（已有链路）追平；CSS 只保留 100% 铺满。
