# 同一会话被重复拉起 CLI 进程（2026-11-15 实测）

> 现象：用户只开了一个聊天，却在同一时段看到多个 `claude -p --resume c118b305…` 进程；
> 伴随 Gradle 互抢、提交重复、后台子代理被杀。用户明确表示没有另开会话。

## 一、实测证据

- 所有相关进程的会话参数**完全相同**：`--resume c118b305-c726-4025-9d4a-6aebd2660659`，
  不存在第二个会话 ID。
- 进程启动时间与用户消息/重连时刻对齐：`12:55`、`13:02:18`、`13:02:37`、`13:02:42`、`13:52:16`；
  13:02 的 25 秒内起了 3 份，符合「重试/重连各起一份」。
- 进程父子链：每份 CLI 都有自己的 proot 父进程（`libproot.so … claude -p --resume <同一 id>`），
  说明是 App 引擎桥重新 spawn，而不是会话内 fork。
- 旧进程并非永久泄漏：13:02:42 起的那份在 13:52 已退出；问题在**重叠窗口**——
  上一轮还在执行时新进程已开始执行同一份对话。

## 二、影响

| 影响 | 具体表现 |
| --- | --- |
| 重复施工 | 两份进程同时按同一份对话继续，先后修改同一批文件并各自提交；出现「改动被另一个实例抢先提交」 |
| 构建互踩 | 各自运行 Gradle；`--stop`/daemon 争抢导致对方构建以 144 退出；KSP 目录被清 |
| 后台子代理被杀 | 会话进程切换时，后台 qa/optimizer 被 teardown，本轮共被中断 3 次 |
| 误导判断 | 容易误认为存在「另一个用户/第三方会话」，实际是同一会话的并行实例 |

## 三、建议修复（App 侧，引擎桥）

1. **同会话串行化**：该会话已有 turn 在跑时，新消息只入队，不 spawn 新 CLI。
2. **先回收再拉起**：重连/重启前先确保旧进程退出（SIGTERM → 等待 → SIGKILL），
   或复用同一进程的长连接，不要「新起一份 + 旧的不动」。
3. **进程归属登记**：按 `sessionId` 记录活跃 CLI PID；发现同会话已有进程时拒绝再 spawn（打日志告警）。
4. **重连去重**：短时间内的多次重连合并为一次（当前 25 秒内起了 3 份）。
5. 退出/崩溃时清理：`--kill-on-exit` 已传，但需确认 App 侧监听进程退出并回收状态。

## 四、本次会话的处置

- qa/optimizer 被多次中断后，改为「重派 + 主编自查」双轨，结论已记录在
  `feedback-notebook-review-2026-11-15.md`。
