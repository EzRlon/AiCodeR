# 增强计划评审包（供外部模型审核）

> 日期：2026-10-24。本文自包含全部背景，无需项目上下文即可审阅。
> 项目：AiCode——运行在安卓手机上的 AI 编程助手 App（Kotlin，Android，单一大 :app 模块）。
> 请重点审核第八节列出的 8 个问题；若发现方案冲突、数据不可信、更优替代，请逐条指出。

---

## 一、背景与硬约束

1. App 自带 PRoot 容器（musl Alpine rootfs）跑在**普通用户无 root 的安卓手机**上，AI 在容器内帮用户开发；容器生态（apk 包源、用户脚本、一键安装环境）依赖 Alpine+proot，整体迁移等于重做半个 App。
2. App 自身也在容器内编译迭代：Gradle 8.14 + AGP 8.9.3 + Kotlin 2.2.21 + KSP2 + R8 8.13.19，单一大 :app 模块（585 个 Kotlin 文件）。
3. 通用 Gradle 优化（build cache、parallel、configuration cache、静态版本号、lintVital 禁用）在调研前**已全部配齐**，官方文档路线已到头。
4. 用户约束：目标定案为「agent/子代理更强更快更准；编译/QA/最终产物更快更稳；会话更懂用户、承载长期项目；多供应商模型自动检测+智能分配（涉成本/未配置供应商需问用户）」；**本地模型不集成不考虑**（用户拍板）；同题只留最优方案，计划内不重复不冲突。

## 二、实测数据（本机，PRoot 容器内，均为单次测量并已标注方差风险）

| # | 场景 | 配置 | 耗时 | 判读 |
|---|---|---|---|---|
| 1 | 空跑（39 task 全 up-to-date，冷 daemon） | in-process + Jetifier | 1m01s | PRoot 固定底价 |
| 2 | 空跑（配置缓存命中） | 同上 | 1m13s | 固定底价 ~1 分钟 |
| 3 | 增量编译（单文件 ±1 行注释，全新内容） | in-process + Jetifier | 7m45s | 真实编译 |
| 4 | 同上（另一新内容） | **daemon** 策略 | **6m05s**（Kotlin 4m33 + KSP 1m27） | 比 in-process 快约 23% |
| 5 | 同内容对照 Jetifier 开关 | daemon + **Jetifier=false** | 1m22s | compile 命中缓存 → **Jetifier 对本项目依赖字节级零改动，可安全关闭**；artifact transforms 重跑 78s 为一次性代价 |

关键归因：增量编译大头是 Kotlin/KSP 纯 CPU 计算（换容器无解）；PRoot 主要放大 IO/进程创建（那 1 分钟固定底价）。PRoot 量化参考：Termux 官方基准 proot 综合性能比原生低 44%；DroidDeck 实测每 syscall 15–60µs vs 原生 0.5µs（30–120 倍）。

实验方法学已标注局限：单次测量有方差（官方 gradle-profiler 基准需预热+多轮，手机上要数小时，暂不做）；关键取舍可用 3 轮均值复核。曾发生一次「文件内容撞历史缓存导致 FROM-CACHE 假优化」，已识别并改用全新内容重测。

## 四、方案裁决表（同题只留最优，含否决记录）

| 问题 | 选定方案 | 否决的备选（理由） | 依据 |
|---|---|---|---|
| 编译策略 | Kotlin daemon（+23%） | in-process（实测慢 23%）；模块化拆分（收益真实但工程大，单列架构项） | 本机 A/B |
| Kotlin 静态扫描 | detekt CLI 独立进程，只扫改动文件 | Gradle 插件方式（与构建抢锁）；Android Lint 增量（领域不同，资源/清单问题由构建期兜住） | 实测 4s/文件 |
| QA 上下文 | diff + 一跳调用邻居（预算封顶） | 全文件通读（token 爆炸+长回合卡死前科） | 腾讯 2026 实证：静态告警 76% 误报，LLM 过滤消除 94–98% |
| 审查时序 | qa 只读审查与主线程构建并行 | 串行等构建完再派（浪费一段等待） | qa 已禁自跑构建，无锁冲突 |
| 模型分配 | 任务类型静态路由为主 + 失败升级级联兜底 | 训练型路由器 RouteLLM 类（需训练数据，移动端过重）；LLM-as-Router（每单多一次调用贵） | ETH 2026 统一框架论文：路由+级联混合持续优于单用；FrugalGPT 级联降本最高 98%；BEST-Route 采样共识再减 15–30% 不必要升级 |
| 提示词装配 | append-only 缓存友好布局：静态前缀固定（tools→system→messages），动态只追加尾部，会话中段不改工具表 | 无 | Anthropic 官方：缓存读成本约 1/10、长提示延迟 -85%；DeepSeek 磁盘缓存默认开启前缀命中重用；Claude Code 生产实践 |
| 长会话上下文 | 压缩优先（已定案）+ 输出落盘+FTS 检索 | 推翻重来 | DeepSeek V4 CSA/HCA 架构（KV 压缩 4 倍+top-k 选择）与该思路同构，方向获印证 |
| 容器 | 维持 PRoot，容器内优化+重活云卸载 | chroot/LXC（需 root）；AVF/KVM（仅 Pixel 8+ pKVM，强隔离难嵌入）；整体迁 Termux bionic（生态重写） | Termux 基准、DroidDeck 逐 syscall 实测；中期可选 proot seccomp 补丁（DroidDeck 已验证路线） |
| 静态分析+LLM 分工 | 静态工具找候选、LLM 只核真伪 | LLM 全量自查 | arXiv 2601.18844（腾讯）、LLM4PFA（过滤 72–96% 误报） |

## 五、增强计划（四目标 + 落地项，含排期顺序）

**目标一：agent 与子代理更强更快更准**
- 1.1 Harness 借鉴施工（已深研完毕，源码级报告）：三大直接嫁接项=①超长输出 spill 落盘（preview+路径+行号，按需读）②压缩崩溃安全锁（start/summary/end 三事件 log-only+孤儿锁检测）③子代理持久 catalog（报告归档可追问）。改造后借鉴=waterfall 拦截链→Kotlin 责任链、step-owned 工具准入、UI 中立 card、worktree 隔离纪律。明确不引入 Cordis 插件框架整体。
- 1.2 意图理解三层制（写进意图路由提示词）：低模糊=直接做；中=动手前复述确认；高=选项式澄清。
- 1.3 评测集：50–100 条「用户原话→期望行为」回归打分——所有「更准」的裁判。
- 1.4 提示词缓存友好装配（见裁决表；与「按模型分档压缩」合并为同一施工项，因改同一段消息装配代码）。
- 1.5 子代理结果缓存：同 diff 范围审查结果可复用。

**目标二：编译/QA/最终产物更快更稳**
- 2.1 A/B#4：正式包恢复 build cache（已暂停等并行会话结束；坏缓存复发则维持 --no-build-cache）。
- 2.2 最终包五项优化清单（性能/功耗/R8）从人工纪律升级为脚本自检（apkanalyzer 体积差分、启动路径、keep 规则核对）。
- 2.3 架构级（单独拍板）：适度模块化拆分（只拆低扇出叶子，官方指南警告过细开销）；proot seccomp 补丁实验；重活云卸载。

**目标三：会话更懂用户、承载长期项目**
- 3.1 项目任务账本产品化：跨会话任务状态（排队/进行中/完成/验收）App 自动维护，新会话自动载入。
- 3.2 用户画像自动归纳：纠正即沉淀，冲突检测。
- 3.3 项目知识库：领域笔记沉淀+检索注入。

**目标四：多供应商模型自动检测+智能分配**
- 4.1 自动探测：复用现有 ModelApiService.fetchModels/testModel（现为手动），静默探测+存「模型能力画像」（可用性/延迟/成本档）。
- 4.2 智能分配：按裁决表方案；涉成本跃升或未配置供应商先问用户。
- 4.3 隐私红线：只用用户已配置 key，不外发，失败不阻塞。
- 4.4 本地模型：不集成不考虑（用户拍板），已有功能保持现状。

**DeepSeek 生态小落地项**：providers 预设核实（alias `deepseek-flash` 已自动路由 V4.1-Flash-1017）；Search API 源（$0.75/千次）；错峰定价用于定时任务。

**排期顺序**：评测集先行（裁判）→ A/B#4 → 目标四（基础最好）→ Harness 借鉴施工 → 3.1/3.2/3.3 → 2.2 → 架构级单独拍板。

## 六、风险与回退

1. A/B 数据为单次测量，关键取舍需 3 轮均值复核；已识别并规避过缓存假命中。
2. detekt 2.0 alpha 的 --report/--create-baseline 落盘有缺陷（只输出到控制台）；轻量模式漏报空指针类 bug，完整模式需 classpath——待补。
3. 正式包 build cache 曾有坏缓存坑（并行构建污染 KSP 产物），A/B#4 需在串行纪律下验证。
4. Jetifier 关闭虽实测编译层零改动，release 全任务链（打包/资源）以 A/B#4 一并验证。
5. Harness 借鉴均为「思想移植」非代码引入（TS vs Kotlin），无许可证污染风险（MIT）。
6. 双会话并行构建会污染缓存——已建立「开工前对 git log+另一会话状态」的续作纪律。

## 七、明确不做（防发散）

本地模型集成；Cordis 插件框架整体引入；liveshare 远程观看；PTC run_code；训练型路由器；AVF/KVM 作为主容器；chroot（需 root）；整体迁移 Termux 模式。

## 八、请审核的重点问题（给评审者的指引）

1. A/B#4（daemon +23%、Jetifier 关闭）是单次测量结论，是否足够支撑保留？是否必须 3 轮均值？
2. 「审查与构建并行」是否有我们没想到的隐患（除已知的 Gradle 锁与缓存污染）？
3. 模型分配选「静态任务路由+失败级联」而否决训练型路由——在多供应商、模型画像动态变化的场景下是否合理？
4. 提示词缓存友好布局与「按模型分档压缩」合并施工，是否有隐藏冲突（压缩会改写历史消息→击穿前缀缓存）？
5. detekt 轻量模式漏报问题：补 classpath 的完整模式 vs 换 Android Lint，哪个是更优解？
6. 容器决策「维持 PRoot」在 1 分钟固定底价 + 增量编译 6 分钟的现实下是否仍是正确取舍？
7. 评测集（50–100 条）设计与维护成本是否被低估？
8. 四大目标排期顺序是否有依赖倒置？
