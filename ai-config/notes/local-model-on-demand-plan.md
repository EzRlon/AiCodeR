## 二、目标与非目标

### 目标
用户想用本地模型时，在 App 里点几下就能用上：**检测设备 → 推荐合适的小模型 → 下载 → 启动 → 自动接入供应商**，全程不用碰终端。

### 非目标（明确不做，防止范围膨胀）
1. **不内置模型文件**（APK 体积不动，模型一律按需下载）。
2. **不引入 JNI/MNN 原生推理**（继续走容器 llama.cpp，复用已有脚本）。
3. **不做常驻后台服务、不做开机自启**（违反功耗纪律）。
4. **不做自动下载**（必须用户在确认页点「开始下载」，显示体积与流量）。
5. **不宣称能替代云端模型**（能力边界写在界面上，见第六节）。

### 与 2026-10-24 决策的关系
2026-10-24 曾拍板「本地模型不集成、不考虑」。本方案把范围收窄为**按需下载的设备内模型 + 用完即停**，不改变「不内置、不常驻」的初衷，属于对原决策的部分放开。如果用户仍不认可，则本方案不启动。

## 三、核心设计：什么时候才算「满足条件」

「条件本地模型」的落地 = 一道**设备体检**，在用户点开本地模型卡片时立即执行（纯本地，不联网，1 秒内出结果）。

### 3.1 检测项
| 检测项 | 取值方式 | 作用 |
| --- | --- | --- |
| 可用内存 | App 侧 `ActivityManager.MemoryInfo`（`availMem`/`totalMem`） | 决定最高可跑档位 |
| 数据分区剩余 | `StatFs` | 判断能否装下模型 + 倍率余量 |
| CPU 架构 | `Build.SUPPORTED_ABIS` | 非 arm64 提示不支持（容器 llama.cpp 包匹配） |
| 大核线程数 | `Runtime.availableProcessors()` | 推荐 `-t` 值（封顶 4，避免全核发热） |
| 容器是否就绪 | 本地容器 Alpine 是否可用 | 不可用 → 引导先建容器 |
| 引擎是否已装 | 容器内 `llama-server --version` | 已装则跳过第 2 步 |

### 3.2 推荐档位表（体积/内存为估算，速度标「待真机实测」）

| 档位 | 可用内存门槛 | 模型（GGUF Q4_K_M） | 文件体积 | 运行内存峰值（估） | 预期速度（估） |
| --- | --- | --- | --- | --- | --- |
| 保守（默认） | ≥ 2.0 GB | Qwen2.5-0.5B-Instruct | ≈ 470 MB | ≈ 0.9 GB | 8–20 token/s |
| 均衡 | ≥ 4.0 GB | Qwen2.5-1.5B-Instruct | ≈ 1.0 GB | ≈ 1.8 GB | 4–8 token/s |
| 高配 | ≥ 8.0 GB | Qwen2.5-3B-Instruct | ≈ 2.0 GB | ≈ 3.2 GB | 2–4 token/s |
| 极客（手动解锁，强警告） | ≥ 12.0 GB | Qwen2.5-7B-Instruct | ≈ 4.7 GB | ≈ 6.5 GB | 1–2 token/s |

- 模型仓库：`hf-mirror.com/Qwen/Qwen2.5-<档位>-Instruct-GGUF`（官方 HuggingFace 兜底），文件名同构（0.5B 已在脚本中验证为 `qwen2.5-0.5b-instruct-q4_k_m.gguf`，其余档位下载前用 HF API 校验真实文件名，不硬编码猜测）。
- 存储要求：`模型体积 × 2`（下载临时文件 + 成品）+ 1 GB 余量。
- 条件不满足时：卡片红字写明原因（「可用内存 1.2 GB，低于最小值 2.0 GB」），并保留「仍要下载」的高级入口（二次确认 + 说明可能卡顿/OOM）。

## 四、体验流程（App 内四步，全自动衔接）

入口：设置 → 模型 → 添加供应商 → 预设「本地模型（llama.cpp）」；同时在该预设卡片上显示状态徽章（未安装 / 已安装未运行 / 运行中）。

### 第 1 步：体检与推荐（本地，即时）
显示体检结果表 + 推荐档位（默认选中「保守」，可切档），显示下载体积、预计耗时、占用空间。

### 第 2 步：装引擎（约 20–60 MB）
直接复用 `install_scenario_localmodel`（不重写脚本），由 App 侧在容器内执行，输出实时打到进度面板。失败分支：
- 非 Alpine 容器 → 提示「本地模型仅支持 Alpine 容器」，给 Ollama 降级选项（1 GB+，需用户明确同意）。
- 网络失败 → 可重试，脚本幂等。

### 第 3 步：下载模型（默认 hf-mirror，官方兜底）
- 容器内 `wget -c` 断点续传，落到 `~/.aicode/local-llm/models/`。
- 进度：轮询目标文件字节数 / 预期字节数（每 1 秒一次，前台可见时才轮询，离开页面即停）。
- 可暂停、可取消（取消只删未完成的 `.tmp`，不删已完成模型）。
- 完成后校验：字节数下限 + 头部 GGUF 魔数；不通过则该档位报「文件损坏，可重试」。

### 第 4 步：启动并接入
- 端口：从 8080 起探测，占用则顺延到 8090。
- 启动命令：`llama-server -m <模型> --host 127.0.0.1 --port <端口> -c 4096 -t <线程数>`，PID 写 `~/.aicode/local-llm/run/llama.pid`，日志写 `logs/llama.log`。
- 探活：轮询 llama.cpp 自带 `/health`（超时 60 秒；以真机实测版本行为为准，不支持则退化为 `GET /v1/models`）。
- 接入：自动创建/更新 provider「本地模型（llama.cpp）」，baseUrl 填实际端口，`models` 填实际模型名（gguf 文件名去 `.gguf`，与 llama-server 一致）。
- 收尾：自动发一条 1 token 探活请求，成功 → 「可以开始用了」，失败 → 展示日志末尾 30 行 + 一键复制。

### 运行期管理（新增「本地模型」设置专区）
状态机：未安装 → 安装中 → 已安装未运行 → 启动中 → 运行中 → 已停止 / 出错。
操作：启动、停止、切换模型（换档需重新下载/选择已有）、删除模型、查看日志。
**功耗纪律（硬约束）**：
- 不做常驻守护、不做开机自启；
- 无请求闲置 10 分钟自动停止（前台服务记录最近请求时间）；
- App 退到后台超过 10 分钟停止服务（可在专区关闭该策略）；
- 启动时清理孤儿进程：读 PID 文件，进程存在但端口不健康 → 直接 kill 后重启，避免 App 崩溃后残留吃电。

## 五、实现拆解（按可独立交付的分期）

### P0（本批，一次做完即可用）
1. `localmodel-service.sh`（新脚本，随 assets 下发）：`start/stop/status/logs/switch`，含端口探测、PID 文件、孤儿清理、健康检查。
2. App 侧「本地模型」专区（设置 → 模型）：体检表、档位选择、四步进度面板、启停按钮、日志抽屉。
3. 预设卡片状态化：`providers.json` 的 tags 去掉命令式说明，改为状态驱动文案。
4. 下载进度轮询 + 取消。
5. 聊天侧友好化：本地 provider 连接失败时，提示「本地模型服务未运行 → 去启动」，附跳转。

### P1（下一批）
6. 多模型库：已下载模型列表、占用统计（接入现成 [`StorageUsageScanner`](../../app/src/main/java/com/aicode/feature/settings/domain/service/StorageUsageScanner.kt)）、删除释放空间。
7. 下载队列与 sha256 校验（体积 + 魔数之上再加内容校验）。
8. 闲置自动停止的可配置策略 + 停止后 provider 状态同步。
9. 失败诊断：OOM 识别、日志摘要直接喂给 AI 让用户问「为什么跑不起来」。

### P2（看需求）
10. 在线商店新增「本地模型」tab（模型清单可在线更新，不必发版）。
11. 更多量化档位（Q5/Q8）、视觉模型（mmproj）。
12. 与「多供应商智能分配」结合：把简单任务路由到本地，复杂任务走云（涉及成本/质量权衡，需单独设计）。

## 六、必须诚实告知用户的能力边界

1. **0.5B 级模型撑不起完整 agent 工作流**：工具调用、长上下文、大文件 diff 编辑基本不可用。本地模型的实际用途是：离线兜底、简单问答、短文本改写/翻译、隐私敏感内容不外发。
2. **上下文默认 4096**：AiCode 的系统提示 + 项目上下文很容易超，超了会报错或截断，界面需提示「建议只用于简短对话」。
3. **是真发热、真耗电**：持续推理 10 分钟以上机身明显升温，插电建议写在提示里。
4. **速度取决于设备**：上表为估算，交付前必须在真机实测校正，未实测的档位标注「未实测」。

## 七、风险与待实测项

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| 容器 OOM 拖死 App | 低端机（2–3 GB）跑 1.5B 以上可能被系统杀 | 档位门槛硬卡 + 峰值监控（`free` 轮询）+ 建议降档 |
| 孤儿进程 | App 崩溃后 `llama-server` 残留耗电 | PID 文件 + 启动前清理；停止按钮二次确认 kill |
| PRoot 下多线程性能差 | `-t` 过大反而变慢 | 默认 `min(大核数, 4)`，实测调 |
| 模型下载不稳定 | hf-mirror 限速/断连 | 断点续传 + 双源切换 + 可暂停 |
| 端口被占 | 多次启动端口漂移，provider baseUrl 要跟着变 | 启动成功后才写 provider，旧端口配置自动更新 |
| `/v1/models` 返回名不一致 | 影响「拉取模型」功能 | 以 gguf 去后缀为准，拉取结果做归并去重 |

## 九、建议的落地顺序

1. 先做 P0 的服务脚本 + 真机跑通「手动点完四步」，把真实速度/内存/发热数据填回本方案第三、六节；
