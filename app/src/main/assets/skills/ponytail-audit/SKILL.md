像一位刚接手这个仓库、出事会被叫起来处理的资深开发者那样审计它。重要度顺序：正确、安全、扛得住负载、有测试、快、精简。精简同样重要：多出的每一行以后都要有人读、有人测、有人修。这是用户要的报告，就给全。

## 1. 先画地图

- 审计用户点名的范围：某个目录、某个包，或整个仓库。什么都没点名时，审计整个仓库。
- 读 README、部署与构建配置、依赖清单、入口点（main、路由、处理器、任务、CLI 命令）与测试。
- 找出预期负载：一个人跑脚本，还是很多用户与进程同时用。按这个负载判断规模问题，并说明你假设的是哪种负载。
- 端到端追主链路：数据从哪进来、存了什么、往哪出去。这些路径要读全：用户输入、钱、认证、数据写入、后台任务、进程间共享的东西。
- 仓库很大时：在出错代价最大的地方深挖，而不是逐文件过。说明哪些部分你没读。

## 2. 找什么

1. **缺陷**：结果错、崩溃、漏掉的边界情况（空、零、最后一项、取整、时区）、调用方与函数实际返回不一致、同一条规则在两处用不同写法。
2. **风险**：安全漏洞（注入、弱随机、密钥写进代码、用户输入缺校验）、数据丢失（异常被吞、写入顺序错、没有事务）。
3. **规模**：单用户没问题、多用户就错——先查后写引发的竞态、每个进程都重复做同一件事、只增不减的内存或列表、逐项查询、大输入上的 O(n²)、必须共享的进程内状态。
4. **缺测试**：有风险的逻辑（一个分支、一个解析器、涉及钱或安全、数据写入）没有能在坏掉时报错的测试。一条好测试就够，不看覆盖率。
5. **速度**：大的变慢是问题。小的收益（热循环里重复干活）只作为建议；有些软件每一毫秒都算数。
6. **精简**：不该存在或可以更小的代码。
   - 删：死代码、没人用的选项、开关与配置、投机的功能
   - 复用：两个辅助函数做同一件事（留一个，点名路径）
   - 标准库/原生：标准库或平台已经能做；某个依赖做的正是几行代码或平台能做的事
   - yagni：只有一个实现的接口、只产出一个产品的工厂、只转发调用的包装
   - 合并：必须一起改的近重复
   - 拆分：一个函数或类干了几件不相关的事，导致难读难测。按职责拆，绝不按行数拆，也绝不拆成只为让函数变短的辅助函数。

## 3. 报告之前先核实

- 每条发现都要有具体情形：「这个输入或这个场景会导致这个错误结果」。给不出情形就不是发现。
- 说某段代码没人用之前，先 grep 整棵树：包括测试、夹具、配置，以及字符串或动态引用。
- 标了 `shortcut:`（旧代码可能写 `ponytail:`）并写明上限的简化写法是决策，不是发现——除非预期负载已经越过那个上限。
- 提能跑通的最小修法。优先能删代码的修法。绝不为问题不需要的地方加层、加框架、加配置。
- 不写风格偏好，不写「建议考虑」，不写含糊的担忧。

## 4. 输出

用用户所用的语言，句子短、用词日常。技术词第一次出现时解释一句。读者可能从没见过这段代码。

开头写「这个仓库是做什么的：」两三句，加上你假设的负载。

然后按三组列发现，重要度高的在前，空组跳过：
- **必修**：缺陷、安全、数据丢失、在预期负载下会坏。
- **应修**：有风险却无测试、真实的慢、重复、职责混杂的函数、不该存在的代码。
- **可选**：小幅提速、更短的写法。

跨组连续编号，方便用户说「修 2 和 5」。最多 20 条；更小的没写进去时，说明还有多少条。每条发现都写全四部分，每部分一两句：

2. **订单记到了错误的日期**（`billing/close_day.py:L40-52`）
   - **这是什么**：每天午夜这个任务结算当天并给当天所有订单出账。
   - **问题**：它从服务器时钟取「今天」，而服务器跑在 UTC。柏林时间 00:30 下的单会被算到前一天。
   - **修法**：在店铺时区里算一次日期：`datetime.now(ZoneInfo("Europe/Berlin")).date()`。一行，其他都不用动。
   - **不修会怎样**：晚下的单显示错误日期，财务得手工改。

结尾写：
- `结论：` 一行——仓库健康，或先说清先修哪几条。
- 有精简类发现时写 `精简：可减 <N> 行、可减 <M> 个依赖。`
- `未检查：` 你没读或没能运行的部分。

什么都没发现时：写「这个仓库是做什么的：」，然后「健康，没有要修的地方。」，再一行说明你检查了什么。

一次性报告，不改任何代码。
