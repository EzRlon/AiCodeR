# 系统化调试

核心原则：**先定位根因，再动手修**。修症状就是失败。

违反这条流程的字面要求，就是违反它的精神。

## 铁律

```
没有一条能红的命令，不许猜原因。
```

Phase 1 没完成，不许提出任何修复方案。

## 何时用

用于任何技术问题：测试失败、构建失败、崩溃、异常行为、性能回退、集成问题。

**尤其在这些时候用**：
- 时间紧（紧急最容易诱人乱猜）
- 「看着就是这一行」的直觉很强
- 已经修过好几版都没好
- 不完全理解问题

**不要因为「看起来简单」跳过**：简单 bug 也有根因。

## Phase 1：造出反馈回路

**这是全部工作的核心**，其余都是机械操作。

有一条针对**这个** bug 会变红的紧回路，根因一定能找到；没有，盯代码再久也救不了。在 Phase 1 上花不成比例的力气。要狠、要有创造力、不许放弃。

### 造回路的手段（大致按优先顺序）

1. **失败测试**：在能触达 bug 的那个接缝上（单元、集成、e2e）
2. **HTTP 脚本**：打运行中的服务
3. **CLI 调用**：固定输入，把 stdout 与已知良好快照对比
4. **无头浏览器脚本**（Playwright 之类）：驱动 UI，断言 DOM、控制台、网络
5. **回放现场**：把真实请求、载荷、事件日志存盘，隔离重放进代码路径
6. **一次性最小工程**：只起出问题的那条链路，依赖用假实现，一个函数调用就能触发
7. **属性 / 模糊测试**：症状是「有时输出错」时，跑上千个随机输入找失败模式
8. **二分脚本**：bug 在两个已知状态之间出现（提交、数据集、版本），把「切到状态 X、检查、重复」自动化，之后可直接 `git bisect run`
9. **差分回路**：同一输入跑旧版与新版（或两套配置），对比输出
10. **人在环脚本**：最后手段。必须人点的时候，用 `scripts/hitl-loop.template.sh` 把人组织进回路，抓到的输出仍回传给 AI

### 收紧回路

回路本身是要打磨的产品。有了回路之后继续收紧：

- **更快**：缓存准备工作、跳过无关初始化、收窄测试范围
- **信号更锐**：断言那个具体症状，而不是「没崩」
- **更确定**：固定时间、固定随机种子、隔离文件系统、断开网络

30 秒的抖动回路和不做差不多；2 秒的确定回路是调试超能力。

### 复现率低的 bug

目标不是干净复现，而是**更高的复现率**：循环触发 100 次、并行、加压、收窄时间窗、注入延时。50% 抖动的 bug 可调，1% 不可调——先把率抬到可调。

### 实在造不出回路

明确停下来说清楚，列出试过什么，向用户要：(a) 能复现它的环境访问权；(b) 脱敏的现场抓包（HAR 文件、日志转储、core dump、带时间戳的录屏）；(c) 允许临时加生产埋点。

**不许在没有回路的情况下进入 Phase 2。**

### Phase 1 完成判据

必须有一条**已经实际跑过至少一次**的回路（展示调用方式与输出，敏感值脱敏），且满足：

- [ ] **能红**：驱动真实 bug 路径，断言**用户描述的那个具体症状**，修好后能变绿。不是「运行不报错」，而是能捕获**这个** bug
- [ ] **确定**：每次运行结论一致（抖动 bug 按上面的高复现率处理）
- [ ] **快**：秒级，不是分钟级
- [ ] **可无人值守**：AI 能自己跑；必须人操作的走 `scripts/hitl-loop.template.sh`

如果你发现自己在回路存在之前就开始读代码编理论——**停下，这正是本技能要拦的失败模式**。

## Phase 2：复现 + 最小化

跑回路，看着它红，确认：

- [ ] 是**用户**描述的那个失败模式，不是碰巧挨着的另一个失败
- [ ] 多次运行可复现（抖动 bug 达到足够高的复现率）
- [ ] 抓到确切症状（报错原文、错误输出、慢在哪），Phase 5 验证修复要靠它

### 最小化

变红之后，缩到**仍然会红的最小场景**：输入、调用方、配置、数据、步骤，一次砍一样，每砍一次重跑回路，只留承重的。

完成标准：**每个剩余元素都承重**——去掉任何一个，回路就变绿。

最小复现能缩小 Phase 3 的怀疑空间（可怀疑的部件更少），并直接变成 Phase 5 的干净回归测试。

没复现且没最小化，不许进入 Phase 3。

## Phase 3：提假设

先出 **3–5 个排序假设**再逐个验证。只提一个会锚死在第一个看起来合理的念头上。

每个假设必须**可被推翻**，写出它预测什么：

> 格式：如果 X 是原因，那么 Y 会让 bug 消失 / Z 会让它更严重。

写不出预测的就是感觉，丢掉或磨锐。

**测之前先把排序列表给用户看**：他常有领域知识能瞬间重排（「我们刚部署了 #3 的改动」），或已经排除过某些。便宜的把关，省大量时间。用户不在就按自己的排序继续。

## Phase 4：埋点验证

每个探针必须对应 Phase 3 的某个预测。**一次只改一个变量。**

工具优先级：

1. **调试器 / REPL 检查**（环境支持时）——一个断点胜过十条日志
2. **定向日志**：打在能区分假设的边界上
3. 绝不「全打日志再 grep」

**每条调试日志带唯一前缀**，例如 `[DEBUG-a4f2]`。收尾时清理就变成一条 grep。不带前缀的日志会活下来，带前缀的会死。

**性能回退分支**：日志通常不是对的工具。先建立基线测量（计时回路、profiler、查询计划），再二分。**先量，后修。**

## Phase 5：修复 + 回归测试

先写回归测试，但**只在存在正确接缝时**。正确接缝 = 测试走的是 bug 在调用现场真实发生的那条路径。

如果唯一能用的接缝太浅（单调用方测试而 bug 需要多调用方、单元测试复制不出触发链路），那里的回归测试只会给假信心。

**没有正确接缝，这件事本身就是发现**：代码结构让这个 bug 锁不住。记下来。

有正确接缝时：

1. 把最小复现变成该接缝上的失败测试
2. 看着它失败。若是靠改代码或改夹具强行弄红的，先 diff 一份干净副本，证明改动真落到了
3. 应用修复
4. 看着它通过
5. 重跑 Phase 1 的回路，打原始（未最小化）场景

## Phase 6：收尾

宣布完成前必须过：

- [ ] 原始复现不再出现（重跑 Phase 1 回路）
- [ ] 回归测试通过（或已记录「无正确接缝」）
- [ ] 所有 `[DEBUG-...]` 埋点已删除（grep 该前缀）
- [ ] 一次性验证工程已删除，或移到明确标记的调试位置
- [ ] 正确的那个假设写进提交信息，让下一个调试的人学到

## 连续修不好时：质疑架构

修到第 3 版还没好，问题通常不在假设，而在架构：

- 每修一处又冒出新问题
- 修复需要大改结构
- 每个修复都在别处造新症状

**停下，质疑根本**：这个模式本身合理吗？是不是在靠惯性硬撑？该重构还是继续修症状？**先和用户讨论，再动第 4 版。**

## 红旗：出现就回 Phase 1

- 「先快速修一下，回头再查」
- 「先改 X 试试看」
- 「一次改几处然后跑测试」
- 「测试先跳过，我手动验一下」
- 「大概是 X，我改掉」
- 「没完全看懂，但也许能行」
- 「再试一次」（已经试过 2 次以上）
- 在追踪数据流之前就给方案

## 找不到根因时

系统化排查后确认是环境、时序或外部因素：

1. 你已经走完流程
2. 写清排查了什么
3. 加合适的处理（重试、超时、更清楚的报错）
4. 加监控/日志供以后查

但：**95% 的「没有根因」是排查不完整。**

## 配套技术

同目录下的细节文档，需要时读：

- `root-cause-tracing.md`：沿调用栈向后追到最初的触发点
- `defense-in-depth.md`：找到根因后在各层补校验
- `condition-based-waiting.md`：用条件轮询替代随意超时
- `scripts/hitl-loop.template.sh`：必须人操作时的人在环复现脚本，复制后改步骤

## 展示命令与现场时先脱敏

要把命令、输出、抓包展示给用户时，**先抹掉密钥**：API Key、Token、密码、Cookie、`Authorization` 头一律替换为 `***`。凭据放环境变量里，不进展示内容。抓包只引用带信号的那几行。脱敏后信息不够判断时，说明情况并问用户。
