# 上下文压缩策略

AiCode 的上下文压缩会把会话历史浓缩成一份「接手摘要」继续工作：占用达到阈值时自动触发（阈值在设置中可调），用户也可在输入栏用 `/compress` 手动触发；接近上限时系统还会出现「交接提醒」，由用户决定是否生成接手摘要、开新会话继续。本技能讲清压缩前、中、后怎么配合，避免「压缩后失忆、信息重取」的反噬。

## 何时建议压缩
- 看占用趋势而不是等满：会话明显变长、工具输出开始频繁截断、回忆较早结论开始吃力时，就可建议用户在输入栏 `/compress` 立即压缩，或提前交接。
- 阶段边界是好时机：一个阶段（调研到方案、方案到实施的一步）收尾、准备进入下一阶段前压缩，摘要干净、边界清晰。
- 暂缓的情形：多步操作正改到一半、关键细节只存在于最近几条消息且尚未落盘时，先把当前步子走完再压缩。

## 压缩前：把关键信息固化到可靠载体
摘要由压缩器生成，你无法直接编辑它；但你可以把信息写进更长寿的地方来提高压缩后的可恢复性——写在最近一轮回复末尾的总结最容易被摘要保留：
- 改过的文件路径与状态：哪些已改完、哪些待改、相关行号或符号。
- 跑过的命令与结论：构建/测试命令、关键报错要点、验证结果。
- 关键决策与约束：为什么这么选、用户定下的规则与偏好。
- 未完成清单与下一步：让接手者（或压缩后的自己）能直接继续。
长流程任务建议维护一个进度笔记（工作区文件或 `todo` 清单）随做随更。

## 压缩后按需补齐
- 以摘要为准继续，不重复已完成的探索：重读文件、重跑命令是压缩反噬的主要来源。
- 缺口定点补回：发现摘要缺失某个细节时，用 `search` 定位 + `readFile` 窗口读把它补回来，仅补缺、不重来。
- tokens-per-task 原则：省 token 的目标是「完成整个任务的总消耗」最小。为防丢信息而在回复里堆积大量冗余，或为极致压缩而损坏必要上下文，都会让总量上升——压缩要「够用」，不追极限。

## 与交接（Handoff）流程配合
- 交接比压缩更彻底：生成接手摘要并开一个全新会话继续。上下文将满时系统自动出现交接提醒，由用户拍板；你也可以在自然阶段点建议用户交接。
- 交接前把「下一步」明确到可执行：新会话没有本会话的模糊记忆，摘要里没写的就不存在——关键文件路径、命令、验收标准要显式列出。

## 用子代理做预防性隔离
- 与其在主线塞满大材料再压缩，不如一开始就把大范围调研、批量通读、全库扫描放进子代理：中间过程占用子代理的上下文，主线只留结论。
- 多个可独立的大块工作拆给多个子代理并行，主线负责汇总与决策；主线天然更短，更少触发压缩。
- 配套使用 `token-saver` 技能：它管「操作层省 token」，本技能管「何时压缩、压缩后如何不丢」。
